This technical introduction explains the concepts behind the Content Authenticity Initiative (CAI) open-source SDK and the basic workflow for reading, validating, and creating Content Credentials.

The SDK implements C2PA functionality for supported asset formats and platforms. Feature coverage depends on the library and release; not every feature in the specification is supported.

## Important terminology

These simplified definitions introduce the main concepts. For authoritative definitions and additional terms, see the [Glossary in the C2PA specification](https://c2pa.org/specifications/specifications/2.2/specs/C2PA_Specification.html#_glossary).

_Content provenance_ is information about the creation, authorship, and editing of a digital asset. _Content Credentials_ record provenance with cryptographic signatures and content bindings that make tampering detectable.

As illustrated below, a _manifest_ contains assertions about an asset, a claim that references those assertions, and a digital signature on the claim.

<img src={c2pa_terms} width="250" />

**Actor**: A person, hardware device, or software product involved in an asset's lifecycle, such as a camera, editing application, or cloud service.

**Asset**: Digital content, such as an image, video, or audio file or stream. The SDK supports [specific asset formats](../sdk-repos/c2pa-rs/docs/supported-formats.md).

**Action**: An operation performed on an asset, such as creating, cropping, or adjusting it.

**Assertion**: Structured information about an asset. For example, an actions assertion can record editing operations. See the [standard C2PA assertions](https://c2pa.org/specifications/specifications/2.2/specs/C2PA_Specification.html#_c2pa_standard_assertions).

**Certificate Authority (CA)**: An organization that issues digitally signed certificates under a defined certificate policy.

**Certificate**: A digitally signed document that binds a public key to a subject under the issuer's policy. A validator must check the certificate and its chain against an appropriate trust policy.

**Claim**: The data that is signed in a manifest. It references assertions using cryptographic hashes, making changes to those assertions detectable.

**Claim signature**: A digital signature created with the signer's private key and verified using the corresponding public key.

**Content binding**: Information associating a manifest with content. A _hard binding_ uses cryptographic hashes of protected content. A _soft binding_, such as a watermark or perceptual fingerprint, helps locate associated manifests even when metadata has been removed or content has changed.

**Ingredient**: A source asset used to create or edit another asset, potentially carrying its own provenance. For example, an edited photograph can reference the original photograph as a parent ingredient.

**Manifest** (C2PA manifest): A set of assertions, a claim, and a claim signature describing an asset's provenance.

**Manifest store**: A collection of manifests associated with an asset. The _active manifest_ describes the current asset and contains content bindings that a validator checks against it.

## How it works

A signed manifest store uses the binary JPEG universal metadata box format (JUMBF). The SDK provides JSON definitions for building manifests and JSON reports for reading them; these are interfaces to the binary representation, not the signed artifact itself. See [Working with manifests](../manifest/understanding.md).

The SDK records cryptographic hashes of protected asset content in binding assertions. The signer signs the claim using a private key. A validator verifies the signature using the public key in the signing certificate, checks the referenced assertions, and compares the content bindings against the asset. Changes to protected content invalidate the [hard binding](https://c2pa.org/specifications/specifications/2.2/specs/C2PA_Specification.html#_binding_to_content).

A C2PA-enabled editing tool creates a new signed manifest for its output, recording relevant actions and referencing source assets as ingredients. It does not simply rewrite the original signed claim.

:::info What validation establishes
Successful validation provides evidence of integrity and, when the signer is trusted under the validator's policy, the source of the signature. It does not prove that the depicted content or every assertion is true or complete. Missing Content Credentials do not, by themselves, indicate that content is false.
:::

### Basic SDK workflow

Once you've [chosen the SDK library to use](../introduction.mdx) based on you runtime environment, the basic SDK workflow is:

1. **Read and validate** an asset with a [Reader](../manifest/reading/reading.md). Distinguish missing credentials from invalid credentials. Inspect the validation results and the `Invalid`, `Valid`, or `Trusted` state; see [Validating manifests](../manifest/reading/validation.md).
1. **Build and sign** provenance with a [Builder](../manifest/writing/writing.md), adding relevant assertions and ingredients and supplying a signer.
1. **Preserve and display** the resulting manifest store and validation results using the storage and UI guidance below.

In the Rust library, a [Context](../sdk-repos/c2pa-rs/docs/context-settings.md) configures verification, trust, network access, and signers. Configure appropriate trust anchors and remote-fetch policies for your application. Equivalent APIs and feature availability vary across language libraries and releases.

## Introduction to public key infrastructure

:::tip
For a video introduction to certificates and key management in the C2PA ecosystem, see [A closer look at private keys and certificates](https://learn.contentauthenticity.org/private-keys-and-certificates) from the Content Credentials Foundations course.
:::

For authentication, C2PA uses _public key infrastructure_ (PKI) and [X.509](https://en.wikipedia.org/wiki/X.509) certificates. The private key creates digital signatures; the corresponding public key verifies them. This does not encrypt the asset or restrict access to it.

A certificate binds the signing public key to a subject under the issuing CA's policy. The manifest includes a certificate chain that lets a validator check signatures back to a configured _trust anchor_, which can be a root or intermediate CA. A valid chain alone does not establish content integrity or factual truth; the other validation checks still matter.

## Signing and certificates

Signing requirements differ between prototyping and production:

1. **Prototype with development credentials.** [Test certificates and keys](../signing/test-certs.md) let you exercise signing, but do not establish public trust and must not be used in production.
2. **Obtain an appropriate production certificate.** Follow the [C2PA certificate requirements](../signing/get-cert.md) and the requirements of your intended trust ecosystem. Conforming generator products must use a certificate chaining to the C2PA trust list; a generic email or document-signing certificate is not automatically sufficient.
3. **Protect the private key.** Use a suitable signer backed by a hardware security module (HSM) or key management service (KMS) for production. A certificate signing request (CSR) contains the public key; it does not require sharing your private key with the CA. Never include production private keys in browser code or distributed applications.

A trusted timestamp from a time-stamping authority (TSA) can establish that the signature existed while the signing certificate was valid, supporting verification after certificate expiry. This is different from a date recorded in an assertion. See [Time-stamps](../manifest/understanding.md#time-stamps).

:::info
For the development-to-production workflow, see [Signing and certificates](../signing/index.md).
:::

### Trust lists

The [C2PA trust list](../conformance/trust-lists.mdx#c2pa-trust-list) contains certificate trust anchors for conforming generator products. A separate TSA trust list supports timestamp validation. Validators must apply the appropriate trust policy; a cryptographically valid signature is not automatically from a trusted signer.

For current lists, legacy [interim trust list](../conformance/trust-lists.mdx#interim-trust-list) support, and tool-specific behavior, see [Trust lists](../conformance/trust-lists.mdx).

## Identity

The identity of the manifest signer is not necessarily the identity of the content creator. A signing certificate may identify an application, device, or organization rather than the person who captured or edited an asset.

:::info
The [Creator Assertions Working Group (CAWG)](https://creator-assertions.github.io/) defines identity assertions that bind identity information and roles to an asset. Their verification and issuer trust are distinct from the enclosing manifest's signature validation. See [Reading CAWG identity assertions](../manifest/reading/reading-cawg-id.md).
:::

## Attaching and storing manifest data

The manifest store must remain associated with its asset, but it does not have to be embedded. Available options depend on the asset format and SDK:

| Storage | How it works |
| --- | --- |
| **Embedded** | The manifest store is stored inside the asset and travels with the file. |
| **Sidecar** | A separate `.c2pa` file accompanies the asset. Keep both files together and supply them to the reader as required by your SDK. |
| **Remote** | The asset contains a reference to an externally-hosted manifest store. The reader needs access to that location. |

### Storing a manifest in file

Embedding keeps the manifest store self-contained, but increases file size by an amount that depends on assertions, thumbnails, certificates, and other resources. It avoids fetching the manifest itself; trust, revocation, or other resource checks may still require network access, depending on configuration.

### Storing a manifest in the cloud

Any developer can host remote manifest stores; this is not limited to Adobe services. Use HTTPS and preserve the reference in the asset. Adobe Content Credentials Cloud is a separate service used by Adobe tools, not a prerequisite for remote storage.

Remote storage alone does not ensure recovery if the reference is stripped. [Durable Content Credentials](../durable-cr/index.md) combine stored manifests with soft bindings and a lookup service to help rediscover provenance. Finding a matching manifest is not a substitute for checking its signature and applicable content bindings.

## Displaying manifest data

:::tip
For video walkthroughs on displaying Content Credentials, see the following from the Content Credentials Foundations course:

- [Progressive disclosure of Content Credentials](https://learn.contentauthenticity.org/progressive-disclosure-of-content-credentials)
- [Reading and validating C2PA data with Javascript in the browser](https://learn.contentauthenticity.org/reading-and-validating-content-credentials)
- [Formatting C2PA data for L1 - L3 disclosures](https://learn.contentauthenticity.org/formatting-c2pa-data-for-display)
:::

Present provenance and validation results meaningfully rather than exposing raw manifest data alone. The [C2PA UX recommendations](https://spec.c2pa.org/specifications/specifications/2.2/ux/UX_Recommendations.html#_levels_of_information_disclosure) describe four _levels of disclosure_:

- **Level 1**: Indicates that manifest data is present and whether it has been validated.
- **Level 2**: Summarizes the manifest data enough to describe how the asset came to its current state.
- **Level 3**: Provides a detailed display of relevant manifest data, including ingredient manifests.
- **Level 4**: Provides the complete data including full detail of signatures and trust signals, for sophisticated, forensic investigatory use.

Your UI should distinguish missing credentials, validation failures, and signer trust. Do not present the presence of a manifest or the Content Credentials pin as proof of trust.

- The Content Credentials pin <img src={cr_pin} width="25" /> shown over the image indicates that the image has Content Credentials (level 1).
- Clicking on the pin displays level 2 information, and an **Inspect** button.
- Clicking the **Inspect** button opens a detailed view, such as [Adobe Content Authenticity Inspect](https://inspect.cr/), for level 3 information.
